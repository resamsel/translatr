## Context

See [proposal.md](proposal.md) - Why. Two independent TypeScript build ecosystems exist side by side: `ui/` is an Nx + npm workspace containing the Angular apps and the `translatr-sdk` library (generated by `openapi-generator` from the server's `openapi.yaml`, using `@angular/common/http` for its services); `cli/` is a standalone Bun project at the repo root with its own `package.json`/`bun.lock`, unrelated to Nx or npm workspaces, that hand-declares its own `Project`/`Locale`/`Key`/`User` response interfaces in [cli/src/api.ts](../../../cli/src/api.ts). Three other in-flight changes (`improve-cli-error-handling`, `support-dotenv-config`, `sunset-python-cli`) already add `translatr-cli` delta specs against the CLI at its current `cli/` path and are not yet archived.

## Goals / Non-Goals

**Goals:**
- Move `cli/` to `ui/apps/cli/` as a registered Nx project, without changing its Bun-based build/compile/dev workflow.
- Replace the CLI's hand-written `Project`/`Locale`/`Key`/`User` interfaces with the generated DTO types already produced for the web UI, so the two consumers can't silently drift.
- Keep every existing CLI command, output, and `.translatr.yml` config behavior identical.

**Non-Goals:**
- Do not give the CLI a runtime dependency on `@angular/common/http`, Angular DI, or any of `translatr-sdk`'s generated services (`ProjectService`, etc.) - the CLI keeps its own `fetch`-based `Api` class.
- Do not migrate the CLI's package manager or bundler from Bun to npm/webpack/esbuild, or fold its dependencies into `ui/package.json`.
- Do not change `translatr-sdk`'s generation pipeline, its Angular-facing API, or its `codegen` Nx target.
- Do not resolve merge order or ordering conflicts with the three other in-flight `translatr-cli` changes beyond noting that they target the same capability - that's a change-management concern for whoever applies/archives these changes, not a design decision here.

## Decisions

### Relocate to `ui/apps/cli/`, keep Bun as the CLI's own toolchain

`ui/apps/*` holds this workspace's runnable applications (`translatr`, `translatr-admin`); `ui/tools/*` holds build-support scripts with no independent package/lockfile of their own. The CLI is a runnable application with its own dependency set, so `ui/apps/cli/` fits the existing convention better than `ui/tools/`.

The CLI keeps its own `package.json` and `bun.lock` inside `ui/apps/cli/` rather than merging its dependencies (`commander`, `glob`, `js-yaml`) into `ui/package.json` and switching its build to Nx's Angular/webpack executors. Alternative considered: fully absorb the CLI into `ui/package.json`'s npm-managed dependency tree and use `@nx/js` or `@nx/esbuild` executors. Rejected because the CLI's value proposition (`bun build --compile` producing dependency-free native binaries for five OS/arch targets) is Bun-specific; forcing it through Nx's npm-oriented executors would require re-deriving that capability and offers no benefit here.

`ui/apps/cli/project.json` wraps the existing Bun scripts with `nx:run-commands`, so `nx build cli`, `nx test cli`, etc. work for anyone driving the workspace through Nx, while `cd ui/apps/cli && bun run build` (today's `cd cli && bun run build`) continues to work unchanged for anyone driving the CLI directly.

### Share generated DTO *types* only, not the generated services

`ui/libs/translatr-sdk/src/lib/generated/model/*.ts` (e.g. `ProjectDto`, `LocaleDto`, `KeyDto`, `UserDto`, `PagedProjectList`, `PagedLocaleList`, `PagedKeyList`, `PagedUserList`) are plain TypeScript interfaces with no framework imports - confirmed by inspection, unlike `generated/api.base.service.ts` and the hand-written `services/*.service.ts`, which import `@angular/common/http` and use `@Injectable`. Only the model interfaces are imported into the CLI; `cli/src/api.ts`'s `Project`, `Locale`, `Key`, `User` interfaces are replaced with (or made type aliases of) `ProjectDto`, `LocaleDto`, `KeyDto`, `UserDto`. The CLI's own `Api` class, its `fetch`-based `request`/`buildUrl`/`handleHttpError` methods, and `ApiError` are untouched.

Alternative considered: have the CLI depend on `translatr-sdk`'s generated services (`ProjectService`, `LocaleService`, ...) directly, retiring `cli/src/api.ts` entirely. Rejected: those services require `@angular/common/http`'s `HttpClient` and Angular's DI container, which would pull the Angular runtime into a Bun-compiled, dependency-free binary - directly against the CLI's cross-platform, no-runtime-required distribution goal (see the existing `translatr-cli` requirement "Cross-platform, dependency-free install" in `sunset-python-cli`'s delta spec).

Alternative considered: copy the DTO shapes into the CLI instead of importing them. Rejected: that's the status quo this change is meant to fix (silent drift risk).

### Type-only import path: CLI's own `tsconfig.json` path mapping

Bun's TypeScript handling honors `paths`/`baseUrl` in the *nearest* `tsconfig.json` to the file doing the importing, not `ui/tsconfig.json`'s workspace-wide `@dev/translatr-sdk` alias (which is consumed by webpack/Angular tooling, not by Bun's bundler). `ui/apps/cli/tsconfig.json` gets its own `paths` entry - e.g. `"@dev/translatr-sdk/models": ["../../libs/translatr-sdk/src/lib/generated/model/index.ts"]` if such a barrel file exists there, or direct relative imports (`../../../libs/translatr-sdk/src/lib/generated/model/projectDto.js`, etc.) otherwise - resolved during the tasks phase by checking what `ui/libs/translatr-sdk/src/lib/generated/model/` actually exports. Because these are `import type` (or plain `interface`) usages with no runtime code emitted, Bun does not need to bundle or execute any `translatr-sdk` module code, and the compiled/bundled CLI binaries carry no `translatr-sdk` runtime footprint.

Alternative considered: publish `translatr-sdk`'s model types as a separate, tiny published/workspace npm package the CLI depends on normally. Rejected as unnecessary indirection for a type-only need; a path mapping (or a thin local re-export file in `ui/apps/cli/src/`) is simpler and avoids introducing a package-publishing step for internal-only types.

## Risks / Trade-offs

- [Bun's module resolution might not honor a relative `tsconfig.json` `paths` entry the same way it honors `baseUrl`-relative imports, or might attempt to resolve `.ts` sibling files in a way that drags in unwanted transitive imports from `generated/` (e.g. `configuration.ts`, which itself has no Angular import but sits next to files that do)] → Verify during implementation with `bun build --compile` and inspect the resulting binary/bundle for any `@angular/*` specifier; if path-mapping proves fragile, fall back to a local re-export file in `ui/apps/cli/src/generated-types.ts` that only re-exports the specific model interfaces needed, keeping the dependency surface minimal and explicit.
- [Relocating `cli/` breaks any developer's local muscle memory (`cd cli && bun run dev`) and any un-updated fork/branch/external script that references the old path] → Root `package.json`'s `i18n:pull`/`i18n:push` scripts, all three GitHub workflow files, and `install.sh`'s documentation are updated in the same change (tasks.md); this is called out as **BREAKING** in the proposal.
- [The three other in-flight `translatr-cli` changes (`improve-cli-error-handling`, `support-dotenv-config`, `sunset-python-cli`) were written against files at `cli/...` paths; if they're applied after this change relocates those files, their task lists' file paths will be stale] → Out of scope to fix here (Non-Goals); flagged in the proposal's "What Changes" so whoever sequences these changes is aware. This change's own tasks only touch paths as they exist today.
- [`ui/apps/cli`'s Bun toolchain being wrapped by Nx `run-commands` could tempt future contributors to add Nx `dependsOn`/caching assumptions that don't hold for a non-Nx-native build] → Keep the `project.json` minimal (thin command wrappers only), documented inline as delegating entirely to Bun.

## Migration Plan

1. `git mv cli ui/apps/cli` (preserves history), then add `ui/apps/cli/project.json`.
2. Update `ui/apps/cli/tsconfig.json` with the new relative depth to `ui/libs/translatr-sdk` and the type-import path mapping (or add a local re-export file), then swap `cli/src/api.ts`'s `Project`/`Locale`/`Key`/`User` interfaces for the generated DTOs.
3. Update root `package.json` (`i18n:pull`/`i18n:push`), `.github/workflows/release.yml` (`cli-binaries` job's `working-directory` and artifact paths), and any other CI/doc references to the old `cli/` path.
4. Run the CLI's existing test suite and `bun run compile:all` from the new location to confirm the build and binaries still work; run `npm run i18n:pull`/`i18n:push` locally to confirm the root scripts still resolve.
5. Rollback: `git revert` the relocation commit(s); no server-side or data migration is involved, so rollback is a pure code revert.

## Open Questions

None - the type-sharing mechanism (path mapping vs. local re-export) is resolved during implementation per the fallback noted in Risks/Trade-offs, and does not change the spec-level behavior or task breakdown either way.
